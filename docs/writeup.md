# Design write-up

## Schema reasoning

The core relationship chain is `organizations → org_members → workflows → workflow_steps / workflow_triggers → workflow_runs → step_runs`. The one deliberate deviation from a pure normalized tree: **`org_id` is denormalized onto every descendant table** (`workflow_steps`, `workflow_triggers`, `workflow_runs`, `step_runs`, `workflow_artifacts`, `external_events`), populated exclusively by `BEFORE INSERT` triggers that copy it from the parent row — never accepted from client input (it's excluded from every insert permission's column list). This turns every row-level permission check from a multi-hop relationship traversal (`workflow_step → workflow → organization → org_members`) into a single-hop one (`workflow_step → organization → org_members`), which is both easier to audit for correctness and cheaper for Postgres to evaluate per request. Because the trigger runs `BEFORE INSERT`, Hasura's permission `check` clause — which evaluates against the row as actually written — sees the correct, server-derived `org_id`, so this can't be spoofed by a client setting `org_id` directly (it isn't even in the allowed column list).

`workflow_artifacts` exists so `db_write` has somewhere concrete to persist a result, separate from `step_runs.output`, matching "saves a result into your own tables" as a first-class queryable table rather than overloading a bookkeeping column. `external_events` is the literal "watched table" for the Database Event trigger type. Statuses and roles are plain `text` + `CHECK` constraints rather than native Postgres enums, so Hasura's generated GraphQL enums and permission `_in` filters stay simple.

The aggregation requirement is a Postgres view, `org_usage_stats` (calls used/allowed, runs this month, avg run duration), tracked in Hasura and exposed as a manual object relationship on `organizations` — so the frontend queries `organization { usage_stats { ... } }` like any other relationship.

## The two permission layers

**Layer 1 (org + role scoping)** lives entirely in Hasura's declarative permissions (`nhost/metadata/databases/default/tables/tables.yaml`). Every `select`/`insert`/`update`/`delete` permission's `filter`/`check` traverses `organization.org_members` and requires a row matching `X-Hasura-User-Id`. Critically, this is **role-blind on read** (any of owner/editor/viewer with org membership can read) but **role-checked on write** — e.g. `workflow_steps`' `owner` insert permission requires an `org_members` row with `role: {_eq: owner}` for *that specific org*, re-derived via the relationship chain, not read from the session variable. This matters because a user can hold different roles in different orgs (owner in Org A, viewer in Org B): the `X-Hasura-Role` header only selects *which* permission ruleset Hasura attempts — the ruleset's own check still requires a real `org_members` row for the org actually being touched, so claiming `owner` while acting on an org you're a viewer in fails the check regardless of the header. This is also how "only an owner can add a `db_write`/`webhook`/`notify`" is enforced *declaratively*, not just documented: the `editor` insert/update permission on `workflow_steps` and `workflow_triggers` includes `type: {_nin: [db_write, notify]}` / `{_nin: [webhook]}` directly in its `check`, so Postgres itself rejects the insert if an editor's session tries it — no application code path can accidentally skip this, because there is no `editor`-role insert permission that lacks it.

**Layer 2 (step-level gating for approval_gate)** cannot be a static row permission, because "can this user unpause this specific run" is a decision that depends on runtime state (is it actually paused? has it already been resolved?) as well as identity — Hasura permissions can't express "and also flip these other rows and resume execution." So `step_runs.approved_by`/`approved_at` have **no Hasura update permission for any client role at all** — the only way to touch them is the `approveStep` Action, whose handler (`functions/approve-step.ts`) re-derives the caller's real role via `getRealRole(userId, orgId)` (a fresh `org_members` lookup using the admin secret, keyed only on `x-hasura-user-id`, which is JWT-verified — never the client-supplied `x-hasura-role` claim) before touching anything. `triggerWorkflowRun` does the identical re-derivation before creating a run. This is the same "never trust the role header, always re-derive from `org_members`" principle as Layer 1, just enforced in application code because the operation is mid-execution rather than a simple row read/write.

## Approval-gate pause/resume

The engine (`functions/lib/engine.ts`) is a single idempotent function, `runWorkflow(runId)`, that walks a workflow's steps in position order and is safe to call more than once for the same run. On reaching an `approval_gate` step it inserts a `step_runs` row with `status: "paused"`, sets the parent `workflow_run.status` to `"paused"`, and returns — no further steps run. `triggerWorkflowRun` calls `runWorkflow` once (running up to the gate); `approveStep`, after validating the approver's role and marking that step's `step_runs` row `succeeded` (or `failed`, if rejected), sets the run back to `"running"` and calls `runWorkflow` again. The loop's resume logic is what makes this idempotent-safe: for each step it checks whether a `step_runs` row for it already exists and is `succeeded`/`skipped` (skip it, carrying its output forward as the next step's input) or `paused` (stop immediately, nothing to do yet) before executing anything — so calling `runWorkflow` on an already-completed run is a harmless no-op, and calling it after approval picks up exactly one step past where it paused. The live subscription (`STEP_RUNS_SUBSCRIPTION`, filtered `where: {workflow_run_id: {_eq: $runId}}`) reflects every state transition — including the `paused` row itself — the instant Postgres commits it, with no polling.
